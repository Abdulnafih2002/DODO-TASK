Part 01

The big picture: what is this project?

You joined Dodo Payments, a company that processes credit-card payments worldwide. A team rushed out a small service called ledger-api that touches card data — but shipped it insecurely: it ran as the all-powerful root user, had passwords in plain text, and no network protection. Card systems must follow PCI DSS, and an audit is coming.

What is DevSecOps? DevOps is building and shipping software quickly. DevSecOps bakes security into every step instead of bolting it on at the end. This project is a tour of exactly that.

The four missions

#TaskGoal in one line
1Harden the workloadLock down the app so it can't be abused.
2Secure CI/CDMake the build/ship pipeline catch security problems automatically.
3Zero-trust networkingMake services prove who they are before they can talk.
4Recon & pen-testAttack the app like a hacker; write a professional report.
Say this out loud“I took an insecure payments microservice and hardened it across three layers — the container, the CI/CD pipeline, and the service-mesh network — then I pen-tested it to prove the controls actually stop real attacks.”
Part 02

What was given vs. what I built

Given to me (the starter materials)

  • The assignment PDF — the 4 tasks and the rules.
  • A starter code repo for ledger-api: a tiny Python/Flask app (app.py), a Dockerfile built on an end-of-life Python 3.6, a requirements.txt of old, vulnerable libraries, and Kubernetes files that ran it as root with plaintext secrets.
  • A neighbour service called reporting (a helper container).

The catch — the app was broken on purpose. These same flaws are what I harden (Tasks 1–3) and exploit (Task 4):

The flaw (given)What's wrongRisk
/import runs yaml.load() on user inputLets an attacker run any command — Remote Code ExecutionCritical
/fetch?url= fetches any URLSSRF — attacker makes the server call internal systemsHigh

Built by me: everything else — the hardened container and Kubernetes manifests, encrypted secrets, admission policies, a full CI/CD pipeline, the Istio zero-trust setup, and the pen-test report. Organised as one folder per task.

Part 03

The tools, in plain English

Grouped by what they're for. The monospace word is the tool; the line under it is what it does.

A · Running the app (platform)

Docker
Packages an app + its dependencies into a container that runs the same everywhere.
Colima
Runs the Docker engine on a Mac (Docker needs a small Linux VM underneath).
Kubernetes
The “operating system for containers” — runs, restarts and connects many of them.
kind
Kubernetes-in-Docker — a whole practice cluster on your laptop, free.
kubectl
The command you type to talk to Kubernetes.
Helm
A “package installer” for Kubernetes — used to install Kyverno.

B · Hardening (Task 1)

securityContext
Settings that lock a container down: non-root, read-only filesystem, dropped Linux powers, seccomp.
ServiceAccount + RBAC
An identity for the app and the minimum rules for what it may do.
SOPS + age
Encrypt secret values so only ciphertext goes into git.
Kyverno
A policy guard at the cluster door that rejects insecure containers.
Pod Security Standards
Kubernetes' built-in “restricted” profile as a second guard.

C · Secure delivery (Task 2)

GitHub Actions
Automation that runs steps on every push — the “pipeline”.
gitleaks
Scans for secrets accidentally committed.
Semgrep (SAST)
Reads your code for security bugs.
Trivy
Scans dependencies + image for known vulnerabilities (CVEs).
Cosign
Signs the image so its origin is provable (keyless — no key to manage). Adds SLSA provenance + SBOM.
ArgoCD (GitOps)
Keeps the cluster matching git; reverts manual changes (“self-heal”).

D · Zero-trust network (Task 3)

Istio (service mesh)
Puts a tiny proxy beside every app to encrypt and control all traffic.
mTLS STRICT
Both sides prove identity + encrypt; plaintext is refused.
Authorization Policy
“Deny everyone except the reporting service.”
SPIFFE identity
A crypto “ID card” per service that rotates automatically; access is by identity, not IP.
NetworkPolicy
A simpler firewall underneath Istio (defense-in-depth).

E · Attacking (Task 4)

subfinder / crt.sh
Find a company's public sites from public records — passive, no attacking.
httpx / testssl
Check a site's tech and TLS setup by reading banners.
nuclei / ffuf / sqlmap
Active testing tools — only against the authorized target.
CVSS v3.1
The industry 0–10 score for how severe a finding is.
Part 04

How I approached each task

Task 1 Harden the workload

Problem
App ran as root, plaintext secrets, no limits, no guardrails.
Approach
Rewrote the Dockerfile to run non-root on a supported Python; wrote hardened manifests (securityContext, CPU/memory limits, health probes, a least-privilege ServiceAccount + RBAC, Service/ConfigMap/Ingress); encrypted the secret with SOPS+age; installed Kyverno + PSS restricted so the cluster refuses insecure pods.
Proof (live)
App runs as uid=10001, can't write files, can't read secrets — and applying the original insecure deployment gets blocked by policy. verified

Task 2 Secure CI/CD pipeline

Problem
No automated security in the build/ship process.
Approach
A GitHub Actions pipeline with gates in order — gitleaks → Semgrep → Trivy → build → Trivy image → Cosign sign + SLSA provenance → push. If any gate fails, the build is blocked.
Fail policy
Hard-block Critical/High that have a fix; vulnerabilities with no fix yet are logged and tracked, never silently passed.
Proof
A green pipeline run, and cosign verify proving the published image is genuinely signed by the workflow. verified

Task 3 Zero-trust mesh (Istio)

Problem
Any pod could talk to the app; traffic wasn't authenticated.
Approach
Installed Istio, turned on mTLS STRICT, wrote a default-deny policy plus an explicit allow for only the reporting identity (by SPIFFE ID, not IP). Added a NetworkPolicy underneath.
Nice detail
The strict Pod Security profile initially blocked Istio's sidecar; the correct fix is the Istio CNI plugin — shows I understand how the layers interact.
Proof (live)
Allowed service → 200, unauthorized identity → 403, plaintext request refused, rotating SPIFFE certificate. verified

Task 4 Recon & pen-test

Approach
Ran the vulnerable app locally (authorized), attacked it, and wrote a professional report with CVSS scores, proof-of-concept, impact and fixes, ranked by risk.
Highlights
Proved Remote Code Execution as root via the YAML endpoint; chained it to steal the live Stripe key + DB password in one request; then retested against the hardened build and every attack failed — directly proving Tasks 1–3 work.
Part 05

Run it again from a cold start

When you shut down, the Docker VM stops and the practice cluster is deleted. Rebuild it once (~10–15 min). Open Terminal and paste each block top to bottom.

0Go to the project & start Docker
cd ~/Documents/GitHub/DODO-TASK
colima start --cpu 4 --memory 8
1Create the cluster & build the app image
kind create cluster --config kind-config.yaml
docker build -t ghcr.io/abdulnafih2002/ledger-api:0.1.0 task1-harden/app
kind load docker-image ghcr.io/abdulnafih2002/ledger-api:0.1.0 --name dodo
2Install the admission guard (Kyverno)
helm repo add kyverno https://kyverno.github.io/kyverno && helm repo update
helm install kyverno kyverno/kyverno -n kyverno --create-namespace --wait
3Task 1 — namespace, policies, secret, app
kubectl apply -f task1-harden/manifests/00-namespace.yaml -f task1-harden/policies/kyverno-policies.yaml
SOPS_AGE_KEY_FILE=~/.config/sops/age/keys.txt sops -d task1-harden/secrets/ledger-api-secrets.enc.yaml | kubectl apply -f -
kubectl apply -f task1-harden/manifests/ -f task1-harden/rbac/personas.yaml
4Task 3 — the Istio mesh
istioctl install --set profile=minimal --set components.cni.enabled=true \
  --set values.cni.cniBinDir=/opt/cni/bin --set values.cni.cniConfDir=/etc/cni/net.d -y
kubectl -n payments rollout restart deploy/ledger-api deploy/reporting
kubectl -n payments rollout status deploy/ledger-api
kubectl apply -f task3-mesh/istio/10-peerauthentication-strict.yaml \
              -f task3-mesh/istio/20-authorizationpolicy.yaml \
              -f task3-mesh/networkpolicy/networkpolicies.yaml
ℹ️
Then test everything with RUN-AND-TEST.md (the “what you should see” guide). Task 2 (the pipeline) runs on GitHub, not your laptop — just open the Actions tab in the browser.
⚠️
The one error you'll hit is connection refused. It means the Docker VM is off — run colima start, wait 30 seconds, and retry. To shut everything down: kind delete cluster --name dodo then colima stop.

Part 07

Interview Q&A — practice out loud

General
QExplain this project in 30 seconds.›

“A payments microservice was shipped insecurely — root container, plaintext secrets, no network policy, and in PCI scope. I hardened it end to end: locked the container down with a strict securityContext and admission policies, moved secrets into encrypted storage, built a CI/CD pipeline that scans and signs every image, and enforced zero-trust networking with Istio mTLS. Then I switched to attacker mode, found a critical remote-code-execution bug, and proved my hardening closes it on retest.”

QWhat is DevSecOps and where is it in this project?›

“Shifting security left — into every stage. Here: workload security (Task 1), pipeline security (Task 2), network security (Task 3), and verification by pen-testing (Task 4).”

QWhat is PCI DSS and why does it matter here?›

“The security standard for handling card data. It's why card numbers must be masked, secrets encrypted, traffic encrypted with mTLS, and access restricted to need-to-know.”

Task 1 · Hardening
QWhat does a read-only root filesystem protect against?›

“If an attacker gets in, they can't write malware or modify the app — I proved this: even after a successful exploit, the container couldn't write a file.”

QWhy run as non-root?›

“If the app is compromised, root inside the container is far more dangerous — it eases container escape and tampering. Running as UID 10001 limits the blast radius.”

QHow did you get the secret out of git?›

“SOPS with an age key encrypts only the secret values; the encrypted file goes in git, the private key never does. At deploy time I decrypt and apply it. I proved no plaintext exists in the repo.”

QKyverno vs. Pod Security Standards — what's the difference?›

“Both block insecure pods. PSS is Kubernetes' built-in profile; Kyverno is a flexible engine where I write custom rules — reject :latest tags, require image signatures. I use both as layers.”

Task 2 · CI/CD
QA CVE has no fix yet — what do you do?›

“I don't silently pass it. I record it with a justification and expiry in a tracking file, keep it visible in the scan report, and re-check when a fix lands. Only fixable Critical/High hard-block the build.”

QWhat is keyless signing and why is it better?›

“Cosign signs the image using the CI's short-lived GitHub identity instead of a long-lived private key I'd have to store and could leak. The signature is recorded in a public transparency log; cosign verify proves the image came from my exact workflow.”

QWhat is GitOps / self-heal?›

“Git is the source of truth. ArgoCD continuously compares the cluster to git and reverts any manual change — so drift can't linger.”

Task 3 · Zero-trust
QWhy identity instead of IP for access control?›

“IPs are reused and spoofable in a cluster. Istio gives each workload a cryptographic SPIFFE identity tied to its service account, so policy is based on who the caller is, and it rotates automatically.”

QIstio authz and a NetworkPolicy — isn't that redundant?›

“No — different layers. NetworkPolicy is L3/L4 in the network plugin and stops traffic that never even reaches the proxy (a compromised or sidecar-less pod). Istio is L7 identity per request. Each catches what the other can't.”

Task 4 · Pen-test
QWalk me through your most severe finding.›

“The /import endpoint ran yaml.load on untrusted input. I sent a crafted YAML payload that executed a shell command — confirmed code execution as root. I then chained it to read the environment and exfiltrate the live Stripe key and DB password in a single request. CVSS 9.8, Critical.”

QHow did you keep scope disciplined?›

“Active testing only against the authorized local target. Recon of the company domain was passive only — public certificate logs and DNS, no scanning — exactly as the rules required.”

QHow do your defenses stop that RCE?›

“Three ways: the code now uses safe YAML parsing; even if exploited, the container is non-root with a read-only filesystem and dropped capabilities; and the secret is no longer plaintext in the environment. I retested — the exploit fails.”

Honesty / judgement
QWhat didn't fully work, and why?›

“NetworkPolicies are applied and correct, but kind's default network plugin doesn't enforce them — in a real cluster with Calico/Cilium they would. I documented this honestly rather than pretend. Istio's L7 policy is enforced live.”

QWhat would you improve with more time?›

“Wire ArgoCD to decrypt SOPS secrets at sync, run a live canary deployment, add Calico so NetworkPolicies enforce locally, and expand the recon into a scored attack-surface inventory.”

Part 08

Glossary flashcards

Container / imageA packaged app; the image is the template, the container is the running copy.
Pod / namespaceA pod is one running unit; a namespace is a folder that groups them.
Root vs non-rootRoot = full power (dangerous); non-root = limited (safe).
SecretA password or key; must be encrypted, never in plain git.
Admission controllerThe bouncer (Kyverno) that rejects insecure pods at the door.
SASTSemgrep — scans your source code for bugs.
CVE scanTrivy — scans dependencies and images for known vulnerabilities.
SigningCosign — a tamper-proof stamp proving an image is genuine.
mTLSBoth sides prove identity and encrypt the traffic between them.
Zero trustNever trust by default; verify every request by identity.
SPIFFEA cryptographic identity (“ID card”) issued to each workload.
CVSSA 0–10 score for how severe a vulnerability is.
RCERemote Code Execution — running any command on the server.
SSRFServer-Side Request Forgery — making the server fetch things it shouldn't.
