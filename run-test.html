Run & Test — Beginner's Guide

Each block explains what to run and what result you should see. Open the Terminal app, paste one block at a time, and press Enter.

Terminal

0 Is Everything Running?

Start with this 30-second health check before testing the individual tasks.

Health check 
docker info >/dev/null 2>&1 && echo "Docker: UP" || echo "Docker: DOWN -> run 'colima start'"
```

kubectl get nodes
kubectl -n payments get pods
```
You should see: Docker: UP, three nodes showing Ready, and application pods showing 2/2 Running.

2/2 means that each pod contains two containers: your application and its Istio security sidecar.

If Docker is down: Run colima start. The Docker virtual machine may occasionally stop.

If the cluster is completely gone: Go directly to Section 6 — Rebuild Everything from Scratch.

1 Task 1 — Hardening

These tests prove that the application is locked down, runs without root access, cannot modify its filesystem, cannot read secrets, and cannot bypass admission security policies.

A Prove the app is not running as root

This also proves that the container cannot write files to its root filesystem.

Non-root and read-only test 
POD=$(kubectl -n payments get pod -l app=ledger-api -o jsonpath='{.items[0].metadata.name}')
```

kubectl -n payments exec $POD -c ledger-api -- id
kubectl -n payments exec $POD -c ledger-api -- touch /test 2>&1
```
You should see: uid=10001(app), not root, followed by Read-only file system.

This means an attacker cannot easily modify application files, replace binaries, or persist changes inside the container.

B Prove the app cannot read Kubernetes secrets

This verifies least-privilege access for the application's service account.

Service account permission test 
kubectl auth can-i get secrets --as=system:serviceaccount:payments:ledger-api -n payments
You should see: no.

C Prove the guardrail blocks the old insecure deployment

Kyverno rejection test 
kubectl apply -f _original/deployment.yaml
You should see: a red error containing denied the request or blocked due to the following policies.

This is a successful security result. Kyverno and Kubernetes Pod Security are refusing to deploy an unsafe root container.

D Prove the secret is encrypted in Git

Encrypted secret check 
cat task1-harden/secrets/ledger-api-secrets.enc.yaml | grep STRIPE_API_KEY
You should see: ENC[AES256_GCM,...] instead of the real secret value.

2 Task 3 — Zero-Trust Mesh

These tests prove that service access is based on authenticated workload identity. The reporting service is allowed, while another identity is blocked.

A Test the allowed reporting service

Allowed request 
kubectl -n payments exec deploy/reporting -c client -- \
```

curl -s -o /dev/null -w 'HTTP %{http_code}\n' http://ledger-api:8080/health
```
You should see: HTTP 200.

The reporting workload has the correct identity and is permitted to communicate with the ledger API.

B Test an unauthorized identity

This creates a temporary intruder pod, attempts the request, and then deletes the pod.

Unauthorized request 
kubectl -n payments run intruder --image=curlimages/curl:8.8.0 --restart=Never \
```

--overrides='{"spec":{"securityContext":{"runAsNonRoot":true,"runAsUser":100,"seccompProfile":{"type":"RuntimeDefault"}},"containers":[{"name":"c","image":"curlimages/curl:8.8.0","command":["sleep","30"],"securityContext":{"allowPrivilegeEscalation":false,"readOnlyRootFilesystem":true,"runAsNonRoot":true,"runAsUser":100,"capabilities":{"drop":["ALL"]}}}]}}'

sleep 8

kubectl -n payments exec intruder -c c -- 
curl -s -o /dev/null -w 'HTTP %{http_code}\n' http://ledger-api:8080/health

kubectl -n payments delete pod intruder
```
You should see: HTTP 403.

The request is blocked because only the authenticated reporting workload identity is authorized.

C Check the mTLS policy

PeerAuthentication policy 
kubectl -n payments get peerauthentication
You should see: MODE: STRICT.

Strict mode requires service-to-service traffic to be encrypted and authenticated through mutual TLS.

3 Task 4 — Local Pen-Test

This test runs the deliberately vulnerable application in a disposable local Docker container. It demonstrates the vulnerabilities and then proves that the hardened version blocks the same attacks.

Important: Run these tests only against the provided local test containers. They are designed for this controlled, offline lab.

Start the vulnerable target

Start vulnerable container 
docker rm -f ledger-target 2>/dev/null
```

docker build -q -t ledger-api:starter task4-recon-pentest/pentest/target

docker run -d --name ledger-target -p 8080:8080 
-e STRIPE_API_KEY="sk_live_9f3a2b7c1e4d8REDACTED" 
-e DB_PASSWORD="P@ssw0rd123" 
ledger-api:starter

sleep 3
```

1 Attack 1 — Exposed card numbers

The application should never return complete payment card numbers.

Read transaction data 
curl -s http://localhost:8080/transactions
You should see: complete card numbers beginning with 4242....

Seeing the complete numbers confirms the sensitive-data exposure vulnerability.

2 Attack 2 — Remote code execution as root

This payload targets the intentionally unsafe YAML importer inside the local vulnerable container.

Local RCE demonstration 
printf '!!python/object/new:type\n  args: ["z", !!python/tuple [], {"extend": !!python/name:exec }]\n  listitems: "__import__(\x27os\x27).system(\x27id > /tmp/pwned.txt\x27)"' > /tmp/rce.yaml
```

curl -s -X POST http://localhost:8080/import 
--data-binary @/tmp/rce.yaml 
-H 'Content-Type: text/plain' >/dev/null

docker exec ledger-target cat /tmp/pwned.txt
```
You should see: uid=0(root).

This proves that an attacker can execute operating-system commands as the root user in the vulnerable container.

3 Retest the hardened application

The following block starts the fixed image with additional Docker hardening and repeats the same attacks.

Start and test hardened container 
docker rm -f ledger-hardened 2>/dev/null
```

--read-only 
--tmpfs /tmp 
--cap-drop ALL

-e TOKEN_SALT=demo 
-e FETCH_ALLOWED_HOSTS=api.example 
ghcr.io/abdulnafih2002/ledger-api:0.1.0 2>/dev/null || 
{
docker build -q 
-t ghcr.io/abdulnafih2002/ledger-api:0.1.0 
task1-harden/app &&

```
docker run -d --name ledger-hardened -p 8090:8080 \
  --read-only \
  --tmpfs /tmp \
  --cap-drop ALL \
  --user 10001:10001 \
  -e TOKEN_SALT=demo \
  -e FETCH_ALLOWED_HOSTS=api.example \
  ghcr.io/abdulnafih2002/ledger-api:0.1.0
```

}

sleep 4

echo "--- cards now masked: ---"
curl -s http://localhost:8090/transactions

echo "--- RCE now rejected: ---"
curl -s -X POST http://localhost:8090/import

You should see: masked card numbers such as 424242******4242 and {"error":"invalid yaml"}.

These results show that sensitive payment data is masked and the unsafe YAML payload is rejected.

6 Rebuild Everything from Scratch

Use this section only when the Kubernetes cluster has been removed or is no longer available.

Run the commands in the order shown. This recreates the cluster, builds the application image, installs Kyverno, deploys the hardened workload, and configures the Istio service mesh.

Complete rebuild 
cd ~/Documents/GitHub/DODO-TASK
```

# Start the Docker virtual machine if it is stopped

colima start --cpu 4 --memory 8 2>/dev/null

# 1) Create the cluster and load the application image

kind create cluster --config kind-config.yaml

docker build 
-t ghcr.io/abdulnafih2002/ledger-api:0.1.0 
task1-harden/app

kind load docker-image 
ghcr.io/abdulnafih2002/ledger-api:0.1.0 
--name dodo

# 2) Install the Kyverno admission guardrail

helm repo add kyverno https://kyverno.github.io/kyverno
helm repo update

helm install kyverno kyverno/kyverno 
-n kyverno 
--create-namespace 
--wait

# 3) Deploy Task 1 namespace, policies, secrets, workload, and RBAC

kubectl apply 
-f task1-harden/manifests/00-namespace.yaml 
-f task1-harden/policies/kyverno-policies.yaml

SOPS_AGE_KEY_FILE=~/.config/sops/age/keys.txt 
sops -d task1-harden/secrets/ledger-api-secrets.enc.yaml |
kubectl apply -f -

kubectl apply 
-f task1-harden/manifests/ 
-f task1-harden/rbac/personas.yaml

# 4) Install the Istio mesh with CNI

istioctl install 
--set profile=minimal 
--set components.cni.enabled=true 
--set values.cni.cniBinDir=/opt/cni/bin 
--set values.cni.cniConfDir=/etc/cni/net.d 
-y

kubectl -n payments rollout restart 
deploy/ledger-api 
deploy/reporting

kubectl -n payments rollout status deploy/ledger-api

kubectl apply 
-f task3-mesh/istio/10-peerauthentication-strict.yaml 
-f task3-mesh/istio/20-authorizationpolicy.yaml 
-f task3-mesh/networkpolicy/networkpolicies.yaml
```

After the rebuild completes, repeat Sections 1 through 3 to verify hardening, zero-trust access, and the pen-test fixes.

Delete everything and free laptop resources

Remove local environment 
kind delete cluster --name dodo
```

colima stop
```

The first command removes the complete Kubernetes cluster. The second command stops the Docker virtual machine.

Tips for Beginners

  • Copy and paste one command block at a time. This makes it easier to identify which step caused an error.
  • When a command appears stuck, it may be waiting for a pod, image, or service to start. Check the Terminal output before cancelling it.
  • kubectl is used to communicate with the Kubernetes cluster.
  • docker is used to build images and run individual containers.
  • -n payments means that the command should run inside the Kubernetes namespace named payments.
  • The pen-test targets the local Docker containers created specifically for this project.
  • The GitHub pipeline is the only section that runs through GitHub rather than entirely on your local machine.
